1. SYSTEM OVERVIEW & ARCHITECTURAL TOPOLOGY
--------------------------------------------------------------------------------
The Note Taking application is engineered as a decoupled, multi-tier system 
following standard client-server architecture principles:

                 +--------------------------------------+
                 |          Client Tier (React)         |
                 | - Single Page Application (SPA)      |
                 | - Client-side Routing (v6)           |
                 | - State Management (Hooks)           |
                 | - Asynchronous HTTP Engine (Axios)   |
                 +-------------------+------------------+
                                     |
                       HTTP / JSON   |   CORS Enabled
                       Port: 3000    |   Port: 5000
                                     v
                 +--------------------------------------+
                 |         Application Tier (API)       |
                 | - Node.js Runtime Engine             |
                 | - Express Framework Middleware       |
                 | - Router & Controller Layers         |
                 | - Input Validation & Parameter Guard |
                 +-------------------+------------------+
                                     |
                       TCP / Binary  |   Connection Pool
                       Port: 3306    |   mysql2 / Promise
                                     v
                 +--------------------------------------+
                 |         Data Tier (MySQL Engine)     |
                 | - notes_app Database                 |
                 | - Relational Integrity (Foreign Keys)|
                 | - ACID Compliant Transaction Support |
                 | - Soft Deletion / Flagged Indexing   |
                 +--------------------------------------+

Key Design Goals:
 - Clean Separation of Concerns: Presentation is strictly isolated from business 
   rules and database queries.
 - Pedagogical Clarity: Code is heavily annotated with beginner-friendly 
   technical explanations without compromising engineering rigor.
 - High Readability & Low Cognitive Load: Avoids bloated third-party abstractions 
   (e.g., Redux, heavy ORMs) in favor of idiomatic core primitives (React Hooks, 
   Express Router, Raw Parameterized SQL).


2. FRONTEND ARCHITECTURE (REACT)
--------------------------------------------------------------------------------
The frontend is constructed as a Single Page Application (SPA) using React 18.
Rendering occurs entirely on the client, minimizing network overhead and 
preventing disruptive full-page refreshes.

2.2 Client-Side Routing Strategy
--------------------------------------------------------------------------------
Routing is powered by `react-router-dom` v6:
 - `<BrowserRouter>`: Synchronizes the UI with the browser's URL history stack.
 - `<Routes>` & `<Route>`: Declarative mapping between URL paths and components:
     * `/`            -> Home (Active notes dashboard)
     * `/create`      -> CreateNote (Creation form)
     * `/note/:id`    -> ViewNote (Detailed view, :id dynamic URL parameter)
     * `/edit/:id`    -> EditNote (Edit form, :id dynamic URL parameter)
     * `/categories`  -> Categories (Category management)
     * `/archive`     -> Archive (Archived notes)
     * `/about`       -> About (Architecture guide)
 - Navigation Hooks:
     * `useNavigate()`: Provides imperative navigation (e.g., redirecting to '/'
       after successful form submission or deletion).
     * `useParams()`: Extracts URL parameters like `id` from `/note/:id`.
     * `useSearchParams()`: Reads and updates URL query parameters (e.g., 
       `/?category_id=2` when filtering from the Categories page).

2.3 State Management & React Hooks Utilization
--------------------------------------------------------------------------------
State management relies exclusively on React's native Hook ecosystem:
 - `useState`:
   Encapsulates local, reactive component state (e.g., `notes`, `loading`, 
   `searchTerm`, `title`, `content`, `categoryId`). Triggers deterministic 
   DOM reconciliation whenever state transition functions are invoked.
 - `useEffect`:
   Handles side-effects such as asynchronous network requests.
   * `useEffect(() => { ... }, [])`: Executes once on component mount.
   * `useEffect(() => { ... }, [dependencies])`: Re-executes when reactive 
     parameters change (e.g., re-filtering when `activeCategoryId` updates).
 - Controlled Form Components:
   Every `<input>`, `<textarea>`, and `<select>` binds its `value` to a React 
   state variable and syncs changes via `onChange={(e) => setState(e.target.value)}`.
   This ensures a single source of truth and prevents DOM drift.

2.4 HTTP Client Abstraction (Axios)
--------------------------------------------------------------------------------
Axios is chosen for network transmission over the native `fetch` API for:
 - Automatic JSON transformation (no manual `response.json()` deserialization).
 - Unified error propagation: non-2xx HTTP responses throw exceptions into 
   `catch` blocks automatically.
 - Intuitive request configuration with query parameter objects (`params: { q, category_id }`).
 - Parallel request orchestration via `Promise.all([fetchNote, fetchCategories])` 
   used in `EditNote.jsx`.

2.5 UI/UX Design System & Modular Styling

 - Design System Tokens:

   tablet, and mobile devices.


3. BACKEND ARCHITECTURE (NODE.JS / EXPRESS)
--------------------------------------------------------------------------------
The backend is constructed as a stateless RESTful service powered by Node.js 
and Express.js.

3.1 Request Pipeline & Middleware Lifecycle
--------------------------------------------------------------------------------
Every inbound HTTP request traverses the following middleware stack:

  Inbound Request
       |
       v
  [ cors() Middleware ]
       | -> Attaches Access-Control-Allow-Origin headers.
       | -> Allows cross-origin requests from React dev server (port 3000).
       v
  [ express.json() Middleware ]
       | -> Inspects 'Content-Type: application/json' header.
       | -> Parses raw request body streams into JavaScript objects (req.body).
       v
  [ Express Router Subsystems ]
       | -> Route match: '/api/notes' -> notesRoutes.js
       | -> Route match: '/api/categories' -> categoriesRoutes.js
       v
  [ Controller Execution ]
       | -> Validates parameters, queries MySQL pool, formats JSON response.
       v
  Outbound Response (HTTP Status Code + JSON Payload)

3.2 Modular Router-Controller Separation
--------------------------------------------------------------------------------
The backend adopts the Model-View-Controller (MVC) architectural separation:
 - `server.js`: Server setup, global middleware registration, port listener.
 - `routes/`: Declares route paths and maps HTTP verbs to controller actions.
   * Route Precedence Rule: In `notesRoutes.js`, the explicit route 
     `router.get('/archived', ...)` is mounted BEFORE `router.get('/:id', ...)`.
     This prevents Express route pattern matcher from mistakenly treating the 
     string "archived" as a dynamic numerical `:id`.
 - `controllers/`: Encapsulates business logic, database queries, and response 
   generation. Keeps route definitions lean and testable.

3.3 Database Connection Pool (mysql2)
--------------------------------------------------------------------------------
Configured in `backend/config/db.js`:
 - Connection Pooling: Rather than creating and destroying a TCP connection for 
   every HTTP transaction, a managed pool of reusable connections is maintained.
 - Configuration parameters:
   * `host`: 'localhost'
   * `user`: 'root'
   * `password`: ''
   * `database`: 'notes_app'
   * `waitForConnections`: true (Queues requests when connection pool is saturated)
   * `connectionLimit`: 10 (Simultaneous open socket threshold)
 - Promise API: Uses `mysql2.createPool().promise()` allowing clean, modern 
   `async/await` syntax and eliminates callback hell.


4. DATABASE SCHEMA & RELATIONAL MECHANICS (MYSQL)
--------------------------------------------------------------------------------
The database layer enforces relational data integrity and structured storage.

4.1 Entity-Relationship Specification
--------------------------------------------------------------------------------
Database Name: `notes_app`

TABLE 1: `categories`
--------------------------------------------------------------------------------
Column Name  Data Type     Constraints                   Description
-----------  ------------  ----------------------------  -----------------------
id           INT           AUTO_INCREMENT, PRIMARY KEY   Unique category identifier
name         VARCHAR(100)  NOT NULL, UNIQUE              Unique category name
color        VARCHAR(20)   DEFAULT '#4a90d9'             Hexadecimal badge color
created_at   TIMESTAMP     DEFAULT CURRENT_TIMESTAMP     Record creation time

TABLE 2: `notes`
--------------------------------------------------------------------------------
Column Name  Data Type     Constraints                   Description
-----------  ------------  ----------------------------  -----------------------
id           INT           AUTO_INCREMENT, PRIMARY KEY   Unique note identifier
title        VARCHAR(255)  NOT NULL                      Note headline / title
content      TEXT          NOT NULL                      Main body content
category_id  INT           NULL, FOREIGN KEY             References categories(id)
is_archived  TINYINT(1)    DEFAULT 0                     0 = Active, 1 = Archived
created_at   TIMESTAMP     DEFAULT CURRENT_TIMESTAMP     Creation timestamp
updated_at   TIMESTAMP     DEFAULT CURRENT_TIMESTAMP     Auto-updated timestamp
                           ON UPDATE CURRENT_TIMESTAMP

Entity-Relationship Diagram:
       +-----------------------+               +-----------------------+
       |      categories       |               |         notes         |
       +-----------------------+               +-----------------------+
       | PK  id (INT)          |<------+       | PK  id (INT)          |
       |     name (VARCHAR)    |       |       |     title (VARCHAR)   |
       |     color (VARCHAR)   |       +-------| FK  category_id (INT) |
       |     created_at (TIME) |  (1 to Many)  |     content (TEXT)    |
       +-----------------------+               |     is_archived (TINY)|
                                               |     created_at (TIME) |
                                               |     updated_at (TIME) |
                                               +-----------------------+

4.2 Foreign Key Constraints & Referential Integrity
--------------------------------------------------------------------------------
 - Foreign Key Definition:
   `FOREIGN KEY (category_id) REFERENCES categories(id) ON DELETE SET NULL`
 - Referential Integrity Rule:
   If an administrator deletes a category from the `categories` table, MySQL 
   automatically sets `category_id = NULL` for all associated notes.
   This prevents orphaned foreign key references without destructively deleting 
   user note contents.

4.3 Soft Delete / Archival Pattern
--------------------------------------------------------------------------------
Instead of permanently purging records when users choose to clean their board, 
a soft archival approach is employed:
 - `is_archived = 0`: Active record displayed on Home dashboard.
 - `is_archived = 1`: Inactive record sequestered in the Archive dashboard.
 - State transitions are handled via `PATCH /api/notes/:id/archive` and 
   `PATCH /api/notes/:id/restore`, modifying a single flag without row cloning.

4.4 Query Performance & SQL Injection Defense
--------------------------------------------------------------------------------
 - SQL Injection Protection:
   All dynamic queries strictly utilize parameterized placeholders (`?`).
   Raw string interpolation (`SELECT ... WHERE title = '${title}'`) is strictly 
   forbidden.
   Example:
     `db.query('SELECT * FROM notes WHERE id = ?', [id]);`
   The MySQL driver escapes special characters and quotes, rendering SQL 
   injection attempts benign.
 - Relational Aggregations (LEFT JOIN + GROUP BY):
   To retrieve categories along with their active note counts in a single query:
   ```sql
   SELECT 
     c.id, 
     c.name, 
     c.color, 
     c.created_at, 
     COUNT(n.id) AS note_count
   FROM categories c
   LEFT JOIN notes n ON c.id = n.category_id AND n.is_archived = 0
   GROUP BY c.id, c.name, c.color, c.created_at
   ORDER BY c.name ASC;
   ```
   * A `LEFT JOIN` guarantees that categories with zero notes are still included.
   * `AND n.is_archived = 0` ensures archived notes do not inflate active counts.

6. END-TO-END EXECUTION TRACE (DATA FLOW LIFECYCLE)
--------------------------------------------------------------------------------
Scenario: User drafts and submits a new note from the Create Note form.

 Step 1 [Client UI]
   - User types in title, selects category "Work" (id: 2), and types content.
   - User clicks "Save Note", triggering `<form onSubmit={handleSubmit}>`.
   - `event.preventDefault()` suppresses the default browser page reload.

 Step 2 [Client Network Layer]
   - Axios prepares an asynchronous HTTP POST request to:
     `POST http://localhost:5000/api/notes`
   - Payload: `{"title": "Sprint Review", "content": "Review v1.0", "category_id": 2}`
   - Header: `Content-Type: application/json`.

 Step 3 [Express Middleware]
   - Request reaches Express server on port 5000.
   - `cors()` verifies request origin is permitted.
   - `express.json()` parses raw network stream into JavaScript object `req.body`.

 Step 4 [Routing Layer]
   - Request matches `app.use('/api/notes', notesRoutes)`.
   - Matches route `router.post('/', createNote)`.
   - Delegates execution to controller function `createNote(req, res)`.

 Step 5 [Controller Layer & Validation]
   - `createNote` validates presence of `title` and `content`.
   - If missing, responds immediately with HTTP 400 Bad Request.

 Step 6 [Database Execution]
   - Controller acquires a connection from the MySQL pool.
   - Dispatches parameterized query:
     `INSERT INTO notes (title, content, category_id, is_archived) VALUES (?, ?, ?, 0)`
     with parameter values: `['Sprint Review', 'Review v1.0', 2]`.
   - MySQL engine validates foreign key constraint against `categories(id)`.
   - MySQL writes row to disk and generates autoincrement `insertId` (e.g. 14).
   - Connection automatically returns to pool.

 Step 7 [API Response]
   - Controller constructs response payload:
     `{ id: 14, title: "Sprint Review", content: "Review v1.0", category_id: 2, message: "Note created successfully" }`
   - Transmits HTTP 201 Created with JSON body.

 Step 8 [Client DOM Update]
   - Axios resolves Promise.
   - `CreateNote.jsx` invokes `navigate('/')`.
   - React Router mounts `Home.jsx`.
   - `Home.jsx` executes `useEffect()` -> `fetchNotes()`, fetching updated notes.
   - React Virtual DOM renders the newly created note on the screen.


7. ERROR HANDLING, VALIDATION & STATUS CODES
--------------------------------------------------------------------------------
HTTP Status Code Guidelines adhered to across the backend:
 - `200 OK`           : Successful query, update, or deletion.
 - `201 Created`      : Successful creation of note or category.
 - `400 Bad Request`  : Client payload failed validation (e.g., missing required fields).
 - `404 Not Found`    : Record matching provided ID does not exist in MySQL.
 - `409 Conflict`     : Duplicate category name violation (MySQL Error 1062).
 - `500 Internal Err` : Unexpected database connection or query failure.

Frontend Error Resilience:
 - Network errors are intercepted in `try / catch` blocks.
 - Loading indicators (`loading` state) prevent UI flickering or premature user interaction.
 - Confirmation dialogues (`window.confirm`) guard critical actions like deletion.


8. SECURITY POSTURE & HARDENING
--------------------------------------------------------------------------------
1. SQL Injection Prevention:
   - Parameterized queries throughout the controller layer eliminate SQL injection risks.
2. Cross-Origin Resource Sharing (CORS):
   - Configured via `cors()` middleware to explicitly allow frontend consumption.
3. Input Sanitization:
   - String trimming prevents empty-string category and note spamming.
4. Foreign Key Constraints:
   - `ON DELETE SET NULL` protects data integrity against dangling pointer bugs.
5. Best-Practice Recommendations for Production:
   - Migrate database credentials from hardcoded `db.js` values to environment 
     variables managed by `dotenv` (`process.env.DB_HOST`, `process.env.DB_PASSWORD`).
   - Add rate-limiting middleware (e.g., `express-rate-limit`) to forestall brute-force attacks.
   - Enable Helmet middleware (`helmet`) for HTTP security header hardening.


9. DEPLOYMENT, LOCAL SETUP & TROUBLESHOOTING GUIDE
--------------------------------------------------------------------------------
Local Prerequisites:
 - Node.js (version 18.x or later recommended)
 - npm (version 9.x or later)
 - MySQL Server (via standalone MySQL, XAMPP, or Docker)

Step 1: Database Initialization
 - Run the complete SQL script located in `database.sql` within your MySQL client.
   ```sql
   source n:/Note-Taking React/database.sql;
   ```

Step 2: Backend Launch
 - Navigate to backend: `cd backend`
 - Install dependencies: `npm install`
 - Verify `backend/config/db.js` credentials match your local MySQL configuration.
 - Start server: `npm start` (Runs on `http://localhost:5000`)

Step 3: Frontend Launch
 - Open a second terminal window.
 - Navigate to frontend: `cd frontend`
 - Install dependencies: `npm install`
 - Start React server: `npm start` (Runs on `http://localhost:3000`)

Common Troubleshooting Scenarios:
 - Problem: `ECONNREFUSED 127.0.0.1:3306`
   Solution: Ensure MySQL service is running in Windows Services or XAMPP Control Panel.
 - Problem: `Access denied for user 'root'@'localhost'`
   Solution: Update password parameter in `backend/config/db.js` to match your MySQL setup.
 - Problem: `EADDRINUSE: address already in use :::5000`
   Solution: A dangling node process is holding port 5000. Terminate it via Task Manager 
   or change `PORT` variable in `backend/server.js`.
